# Proxy Sait

Каталог Telegram-прокси с поиском, фильтрами и копированием ссылки подключения.

## Источники и автообновление

Worker независимо собирает и объединяет следующие списки:

- Собственный файл репозитория: `public/proxies.txt`
- Дополнительный файл репозитория: `data/proxies.txt`
- iwizard7/MTProxy_list: `working.txt`, `stable.txt` и `all.txt`
- 0xRadikal/Free-Telegram-Proxy: `fast/tg.txt`, `stable/tg.txt`, `resilient/tg.txt`, `resilient/tme.txt` и `top100.txt`
- SoliSpirit/mtproto: `all_proxies.txt`

Поддерживаются ссылки MTProto, Telegram SOCKS и SOCKS5, а также Telegram WEB proxy. Ссылки сохраняются отдельно от адресов серверов: одинаковые `server:port` с разными `secret` не затирают друг друга. Одинаковые MTProto-серверы с тем же секретом не дублируются в выдаче, даже когда один источник публикует `tg://`-ссылку, а другой — `https://t.me/`; разные секреты остаются разными ссылками. Проверка TCP ведётся отдельной очередью уникальных адресов: лимит 48 относится к одной партии, а не ко всему каталогу. Cron запускает следующие партии каждую минуту, пока не проверит все найденные адреса; повторная проверка каждого адреса планируется примерно через 5 часов.

Каждый уникальный адрес проходит TCP-проверку партиями по 48. Очередь продолжает обрабатываться cron каждую минуту, а страница автоматически подтягивает результаты следующих партий. Это подтверждает, что порт отвечает, но само по себе не гарантирует успешное подключение к Telegram.

Для MTProto добавлена отдельная глубокая проверка по каждой полной ссылке (включая конкретный `secret`) через GitHub Actions и утилиту на базе `gotd`: выполняется MTProto handshake, затем реальный Telegram-запрос `HelpGetNearestDC`; RTT измеряется до ответа Telegram. Поэтому два секрета на одном `server:port` получают независимые статусы. В карточках MTProto показывается RTT глубокой проверки, а SOCKS5 и WEB пока остаются на TCP-проверке. Endpoint `/proxies.txt` и JSON endpoint `/api/proxies` для MTProto отдают только ссылки с недавним успешным глубоким тестом, а для остальных типов — ссылки с недавним успешным TCP-тестом.

Если отдельный источник временно недоступен, его ранее сохранённые записи остаются в каталоге. Сбой одного источника не мешает загрузке остальных. Если все источники недоступны, предыдущий каталог не стирается. Записи, не встречавшиеся ни в одном источнике 30 дней, удаляются при успешной синхронизации.

Списки источников синхронизируются каждые 5 часов. Проверка накопленной очереди продолжается партиями по 48 адресов каждую минуту, пока очередь не закончится; затем каждый адрес будет перепроверен примерно через 5 часов. Состояние очереди и результаты хранятся в Cloudflare D1. Кнопка «Обновить» принудительно перечитывает источники и запускает следующую партию.

Важно: публичные прокси принадлежат третьим лицам и могут внезапно перестать работать. Не передавай через неизвестные прокси конфиденциальную информацию.

## Мониторинг

Открой `https://proxy-sait.novogodniysait.workers.dev/health` для JSON-отчёта о работе каталога. Он показывает:
- сколько источников настроено, успешно загружено, завершилось ошибкой или ещё не проверялось;
- для каждого источника — URL, статус, число найденных ссылок, проверенных адресов, ответивших и не ответивших;
- общее число найденных ссылок, уникальных адресов, проверенных за последние 6 часов и ожидающих проверки;
- число доступных и недоступных TCP-портов и время последней проверки.

Также доступен машинный endpoint `/api/health`. Данные появляются после первого успешного обновления. Проверка доступности — TCP-проверка порта, не полная проверка подключения к Telegram.

## Деплой

```bash
npm install --save-dev wrangler
npx wrangler login
npx wrangler d1 migrations apply steklo-vpn --remote
npx wrangler deploy
```

Перед деплоем Worker с глубокой проверкой MTProto применить миграцию `migrations/0006_mtproto_deep_health.sql` к D1 `steklo-vpn` (Cloudflare → D1 → `steklo-vpn` → Console → выполнить SQL из файла). Миграции `0005` и `0006` должны быть применены. Затем развернуть Worker.

GitHub Actions workflow `MTProto deep health check` запускается автоматически каждые 5 часов или вручную через Actions → MTProto deep health check → Run workflow. Для первой публикации нужно запустить workflow вручную, чтобы создать ветку `proxy-health` с файлом `mtproto-status.json`. Если публикация ветки завершится ошибкой прав, в Settings → Actions → General включить Workflow permissions → Read and write permissions. Cloudflare Worker читает только JSON-снимок из этой ветки и сохраняет результаты в D1; сами секреты прокси в D1 для глубокого теста не сохраняются, используется SHA-256 ключ ссылки.

Исходный код Worker — `src/worker.js`, статические файлы — `public/`, миграции D1 — `migrations/`.
